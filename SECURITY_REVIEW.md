# Проверка безопасности Chog: Beauty Arena

Дата: **20 октября 2026, Москва**. Статус: **реальные средства пока не включать**.

Проверены исходники на базе локального eded7ff / GitHub 5e686659614a87c2921c78e6be42006fb4ef8992 и исправления этого обновления: контракт, браузерная отправка ставок, timelock, keeper, HTTP/API, зависимости и эксплуатационные риски. Это внутренняя проверка с воспроизводимыми сценариями, не независимый аудит и не доказательство отсутствия всех уязвимостей. Реальная арена не развёрнута; транзакций в Monad mainnet не отправлялось.

## SEC-01: срыв матча и выборочное раскрытие

Контракт проверяет длину ciphertext и наличие commitment, но не доказывает соответствие шифротекста допустимому голосу. Через прямой commitVote можно опубликовать мусор. Число участников увеличится, раскрыть эту запись будет невозможно. Текущее правило отменяет весь матч после reveal deadline и разрешает возвраты.

Воспроизведение: тест «SEC-01: an unstaked holder malformed ballot can veto a fully revealed honest majority». Три честных голоса раскрываются с результатом 2–1; четвёртый, некорректный, отменяет матч. Холдеру не нужна ставка, поэтому минимум 5000 CHOG не устраняет этот сценарий. Он независим от принятого SEC-02.

Исходная подписанная транзакция не меняется. Нарушитель подписывает собственный вызов публичного контракта; контракт не знает, использовался ли сайт. Нарушитель также может заранее создать корректный commitment, опубликовать мусор вместо ciphertext и, увидев остальные раскрытия, самостоятельно вызвать revealVote с известными ему side/salt. Поэтому правило «не раскрылся — не считается и теряет ставку» оставляет выбор, засчитывать ли свой голос после просмотра остальных. Запрет повторного commit это не предотвращает: reveal — другой вызов.

Возможные направления исправления:

- Проверяемое контрактом доказательство корректного шифрования и допустимого бюллетеня. Требует отдельной криптографической разработки и проверки.
- Авторизованный сервис раскрытия, отправляющий только расшифрованные опубликованные бюллетени; самостоятельное раскрытие исключается. Это вводит доверие к сервису, который может цензурировать раскрытия. Нужны правила отказа/восстановления, чтобы честные ставки не конфисковывались из-за недоступности инфраструктуры.

Владелец предложил исключать некорректные голоса без возврата. **Это предложение ещё не внедрено:** требуется выбор модели проверки. Нераскрытие не доказывает злонамеренность. Текущее поведение демо и контракта с полными возвратами сохранено до согласования протокола.

## SEC-03: доступность приложения и раскрытия

Подтверждено публичным RPC https://rpc.monad.xyz: запрос событий за 500 блоков возвращает HTTP 413; за 100 проходит. Keeper использовал 500. Исправлено на максимум 100 блоков, включая последнюю неполную порцию; добавлена регрессия.

Ожидание receipt раньше не имело ограничения и могло остановить следующие матчи. Теперь wait(1, 30000) ограничивает ожидание, а reveal с таймаутом уступает другим матчам. RPC-запросы server/keeper ограничены 15 секундами. **Таймаут не отменяет уже отправленную транзакцию**: следующий цикл перечитывает состояние, но полноценное сохранение pending hashes/nonces и восстановление после перезапуска ещё не реализовано.

Параллельные /api/state?fresh=1 раньше запускали независимые обходы истории. Теперь общий in-flight запрос объединяет обращения; принудительная свежесть ограничена интервалом 1 секунда, обычный cache — 10 секунд. Тест со 100 одновременными fresh-запросами подтверждает один вызов загрузки; отказ RPC освобождает блокировку для повтора. Это не защита от распределённого DDoS.

Остаётся: keeper/server обходят историю; нет сохраняемого индекса/очереди, лимита работы за цикл, production-хостинга, резервного keeper и мониторинга MON/ошибок/отставания. Большая история, отключение RPC/drand, нехватка газа и зависший nonce могут привести к пропуску reveal window. Нужны индекс незавершённых матчей, сохранение событий/транзакций, ограниченная очередь, восстановление и нагрузочная проверка. Settle/claim требуют транзакций: при отключённом keeper/сайте деньги не отправляются сами.

## SEC-04: реальные CHOG и NFT

Проверка только чтением, Monad chain ID 143, блок **114856368**:

- CHOG: Chog, CHOG, 18 decimals. Runtime 45 байт — **EIP-1167 minimal proxy**, реализация 0x7f64ccfeb3e3afd7691ea0ef404e947786cefae8. Нулевые EIP-1967 слоты не означают отсутствия proxy. Owner() недоступен и не доказывает отсутствия других административных функций.
- Genesis: Chog Genesis, supply 1969, runtime 17264 байта. Прочитан опубликованный в MonadScan исходник ChogMint; полный независимый аудит коллекции не проводился. Code hashes и результаты чтения сохранены в security/asset-snapshot.json.
- На странице реализации CHOG проверенный исходник не получен. Это не доказывает наличие эксплойта; поведение и полномочия нельзя объявить полностью проверенными.

**Локальный fork блока 114857107 прошёл:** реальные bytecode/storage CHOG и коллекции, создание/принятие заявки с NFT 299/379, три ставки по 5000 CHOG, результат 2–1, gross по 7500 двум победителям, fee по 75, net по 7425, treasury 150, остаток банка 0. Результат — security/fork-result.json.

Все deployment/переводы выполнялись в одноразовой Ganache EVM, chain ID 1337. Upstream-адаптер разрешает только чтение. Использованы локальное impersonation публичных адресов и фиктивный MON; ключи пользователя не читались. Раскрытия в этом сценарии ручные, без drand. Для совместимости отсутствующий в ответе Monad массив withdrawals нормализован в пустой. Это проверка активов в одном снимке Shanghai EVM, **не проверка консенсуса/gas Monad**, будущих административных изменений или полной криптографии.

Перед live: установить модель доверия внешнему токену, проверить доступную реализацию и провести полный цикл с новым контрактом в подходящем тестовом окружении; подготовить production keeper и аварийный доступ к settlement/claims.

## Проверка средств и состояния

Локальная EVM проверяет:

- Только исходный участник получает выплату; owner/treasury не могут получить её за него. Повторный claim, подмена кошелька/раунда/сети/NFT и повторное раскрытие отклоняются.
- Gross считается до индивидуальной комиссии 1%; draw, one-sided bank и отмена возвращают ставку без комиссии. Treasury получает только комиссии уже полученных выплат; вывод не затрагивает банк другого раунда.
- Вредоносные callbacks токена при deposit/claim получают ReentrancyGuardReentrantCall; дополнительного списания/получения не происходит.
- Налог во входящем переводе откатывает токены, entry и счётчики. Отказ исходящего перевода откатывает claimed и комиссию: участник может повторить claim после восстановления переводов.
- Восемь последовательных сценариев с разными сторонами, суммами и wei-округлением сохраняют баланс: выплаты плюс комиссии не превосходят банк; остаток соответствует целочисленной пыли. Это ограниченная матрица, не исчерпывающий fuzzing.
- Передача активной NFT не снимает блокировку; удаление NFT в mock-коллекции не мешает settlement/выплатам. Чужая заявка, повторное принятие/отмена и повторное начисление статистики отклоняются.

У owner нет функций изменения результата, комиссии/treasury, обновления реализации арены или вывода банков. Settlement/claim не перебирают всех участников. Это снижает соответствующие риски, но не гарантирует отсутствия всех атак. Прямо отправленные токены и пыль могут остаться заблокированными; право владельца забрать весь баланс не добавлялось.

## Браузер, API и инфраструктура

Исправлена гонка смены кошелька во время шифрования/approval: используются захваченные signer/account и идентификатор сессии, проверяются текущие accounts/chain перед запросами подписей. Тесты моделируют смену на обоих этапах и отсутствие commit после неё. NFT-пара и drand beacon теперь читаются из getRound через wallet provider вместо API.

HTTP проверяет размер тела по байтам, отклоняет null/массив вместо объекта; лимит 8192 байта. Добавлены сроки приёма заголовков/запроса 10/15 секунд, ограничения заголовков и запросов на keep-alive соединение. Проверены malformed JSON, oversized ASCII/UTF-8, параллельные запросы, чужой Origin, traversal за пределы public и недоступность deployment API. На live сервер не принимает игровые POST вместо подписанных транзакций.

Просмотрены экранирование надписей, CSP, статические маршруты, cookie-флаги, отсутствие plaintext side/salt до раскрытия. В отслеживаемом дереве не обнаружены .env, keystore или шаблоны приватных ключей; это не полное сканирование внешних хранилищ/истории. CI ограничен contents: read и 10 минутами выполнения.

Production ещё требует HTTPS/reverse proxy с ограничениями соединений/запросов, защищённое окружение keeper, наблюдаемость и восстановление. Компрометация фронтенда способна подменить действия до подписи; чтение раунда из контракта не защищает от подмены JavaScript. Доверие к threshold drand остаётся — см. [модель безопасности](https://docs.drand.love/docs/timelock-encryption/#-security-assumptions).

## Зависимости и инструменты

Lockfile: solc 0.8.30, OpenZeppelin 5.4.0, ethers 6.17.0, tlock-js 0.9.0. Tmp закреплён на 0.2.7; основания предыдущего исправления: [GHSA-ph9p-34f9-6g65](https://github.com/advisories/GHSA-ph9p-34f9-6g65), [GHSA-7c78-jf6q-g5cm](https://github.com/advisories/GHSA-7c78-jf6q-g5cm).

Последний успешный сохранённый npm audit: **36 findings — 5 critical, 22 high, 8 moderate, 1 low**, все пути внутри node_modules/ganache (dev-инструмент). Других путей тот запуск не отметил. Повторные запросы в ходе этой проверки завершились сетевым ECONNRESET: свежий успешный audit не заявляется; зависимости не менялись. Audit --omit=dev включает часть bundled-зависимостей Ganache, поэтому требуется проверять пути.

Ganache нельзя публиковать как production RPC или использовать с production-ключами. До релиза нужен отдельный runtime-образ без devDependencies; тестовый инструмент следует заменить/изолировать. Проверка не включает независимый аудит библиотек, пенетест реального хостинга, нагрузку mainnet или формальную верификацию.

## Воспроизведение и демо

Локально прошли **64 теста**, синтаксические проверки, Solidity-компиляция и сборка браузера. SEC-01 является проходящим тестом существующей атаки, а не исправлением. Наличие зелёного CI не означает готовность протокола к реальным средствам.

    npm ci
    npm run check
    npm run build
    npm test
    node scripts/security-assets.mjs
    node scripts/security-fork.mjs
    npm audit --json

Security-скрипты обращаются к сети только за чтением. Fork — opt-in проверка вне CI; отчёт записывается по переданному CLI-пути. Для повторения после изменения цепочки учитывайте block сохранённого результата: скрипт по умолчанию берёт актуальный снимок.

Демо сохранена отдельно, используется прежний ARENA_STATE_DIR. Перед обновлением сделана согласованная SQLite-копия demo-before-repeat.sqlite: четыре завершённых раунда и десять заявок. История не очищалась; HTTP/EVM-тесты используют изолированные состояния. Демо остаётся с двухминутными раундами, live-контракт — с 24 часами.
